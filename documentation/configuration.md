# Configuration reference

Every environment variable the webapp reads, where it is set, and what happens when it is missing.

**This table is the authoritative list.** The code side of it is a single file —
`webapp/mc-web/src/main/kotlin/app/mcorg/config/ConfigLoader.kt` — and `readConfig()` there is the
only place in `src/main` that calls `System.getenv`. If you add a variable, add it in both places.

Written for MCO-333, which found nine declaration sites and no list: `MODRINTH_URL` declared while
the code read `MODRINTH_BASE_URL`, `TEST_HOST` and `KTOR_LOG_LEVEL` declared but never read, and
several variables read but declared nowhere.

## How failures behave

Configuration is read once at startup and validated by `AppConfig.initOrExit()`, the first
statement of both `main()` entry points (the web app and the ingestion CLI). Three outcomes:

| Severity | When | Behaviour |
| --- | --- | --- |
| **Fatal everywhere** | `ENV` is set to something that does not parse | Log and `exit 1`, in every environment including LOCAL. The environment selects the security posture, so an unparseable value has no safe default (MCO-331). |
| **Fatal outside LOCAL** | A required variable is missing | Log and `exit 1` before Netty binds. |
| **Warning in LOCAL** | A required variable is missing | Log a warning and continue, so a fresh clone runs without a full env file. |

"Required" below means required in the environments named — the app exits at startup without it.

`CreateWebhookSubscriptionStep` directly, authenticated as a world admin, so the user-facing

⁶ Set as a Fly secret and live in production. When absent, the Discord settings section renders a

preview dead-ends at the sign-in page. This was the state of every preview between MCO-333 and
MCO-396: the code default was removed without adding the corresponding deployment value.

The preview's Neon branch is forked from production, so `DEMO_USER=evegul` lands in real worlds —
the reason previews are worth looking at. It is not a secret and is not exposed: the whole preview
sits behind `PREVIEW_PASSWORD` Basic Auth, and the fork is torn down with the app.

⁸ The only two variables **not** read by `readConfig` — logback resolves them itself when it parses
`logback.xml`, before any application code runs, so they cannot go through the loader. `LOG_LEVEL`
sets the root level (mostly third-party noise); `APP_LOG_LEVEL` sets `app.mcorg` separately,
because that is the one that turns on `ValidationSteps`' raw-parameter-value logging. Neither
should be below `INFO` in production — see MCO-337 and the comments in `logback.xml`.

## Production database URLs: pooler vs direct

Three sites name the production database, and **two of them are deliberately different**:

| Site | Endpoint | Mode | Used by |
| --- | --- | --- | --- |
| `webapp/fly.toml` | `ep-withered-truth-a2d65fv7-pooler` | pooled (PgBouncer) | the web app |
| GitHub `production` var `DB_URL` | `ep-withered-truth-a2d65fv7` | direct | Flyway migrations, and the deployed `ingest-scheduler` machine |
| `webapp/scripts/ingest-machine.sh` | *derived from `fly.toml`* | pooled | the manual `--once` smoke test |

Same Neon compute (`br-sweet-base-a241rhcz`, the `master` branch), different connection modes.
Direct for migrations is correct — DDL and session-scoped advisory locks do not want a transaction
pooler in between.

`ingest-machine.sh` used to hardcode a third endpoint, `ep-icy-wood-a2vogqwy-pooler`, which no
longer exists; MCO-334 replaced that with a read of `fly.toml`, so the repo now spells the host
once. Note the remaining asymmetry: `--once` goes through the pooler while the *deployed* scheduler
goes direct, so the smoke test is not a byte-for-byte rehearsal of the nightly run. That gap is
where MCO-348 (session advisory locks through PgBouncer) lives — resolve it there, not here.

## Adding a variable

1. Add the field to `Config` and read it in `readConfig()` (`ConfigLoader.kt`) — nowhere else calls
   `System.getenv`.
2. Mirror the field onto `AppConfig` and its `apply()`.
3. Add a row above.
4. Declare it wherever it needs to exist: `local.env.example`, `test.env`, `fly.toml`,
   `dev.fly.toml`, `prod.yml`, or as a Fly/GitHub secret.
5. Cover the new required/optional combinations in `ConfigLoaderTest`.
